# TrueAngle subscription rollout

Keep PR #7 in draft until hosted billing tests pass and production rollout has been explicitly approved. The Vercel preview is separate from production.

## Test environment

Use the separate Free Supabase project, **TrueAngle Billing Sandbox**, and a Stripe Sandbox with a synthetic USD $29 monthly price. Use environment-specific Supabase keys, Stripe API and webhook signing keys, price ID, and callback URL. Set `BILLING_SANDBOX_SUPABASE_URL` to the isolated project's URL in the Vercel preview. Keep test configuration scoped to the preview or a local server. Seed synthetic data only. The SQL in `supabase/tests/billing-fixture.sql` bootstraps an empty test project's billing and company tables. Apply the billing migration, then run `supabase/tests/billing-assertions.sql`. The assertions roll their changes back.

Complete hosted Checkout with a Stripe test card. Verify the 14-day trial, existing subscriber access, delegated access for eligible companies only, duplicate requests, failed payment through a test clock, recovery through the portal, cancellation, deleted-customer reactivation at $29, and sign-out. Check actual delivery and response codes in Stripe Workbench. Replay a stale event for the current subscription and then an older cancellation after reactivation. Confirm the correct subscription stays in Supabase.

## Production checks before approval

- Reconcile Stripe and Supabase using exact subscription IDs. The November 24 audit found four local rows across five accounts. One owner had no local subscription or Stripe metadata search match. Three local rows said `trialing` past expiration. Stripe confirmed one of those subscriptions active and did not find the other two by exact ID. A fourth local row matched a canceled Stripe subscription. Three other canceled Stripe subscriptions did not match the local current subscription IDs. Resolve the two missing links against the correct Stripe mode/account and historical records. Preserve verified active access and document support decisions for unverifiable accounts.
- The migration seeds a private-to-the-server eligibility record for every existing account. It marks known billing history used and holds introductory eligibility on unverified legacy accounts. Approve any exception only after verifying the account's history. The migration keeps the existing subscription, user, company, and business records.
- Stripe has one enabled v1 snapshot endpoint for `https://trueangle.app/api/stripe/webhook` on API version `2026-04-22.dahlia`. It currently sends `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_succeeded`, and `invoice.payment_failed`. The new handler covers all six. It also handles `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `customer.subscription.paused`, `customer.subscription.resumed`, `invoice.paid`, and `customer.deleted`. Decide which additional events to enable after sandbox verification. Keep the six existing deliveries in place. Enable asynchronous events before offering delayed payment methods, and include `customer.deleted` for the deletion path. Since both invoice success events can represent the same state transition, the handler re-reads Stripe state for each.
- The Stripe event API showed both delivered and failed or pending cancellation events in the last 30 days. It showed failed or pending Checkout completion and invoice-payment-success deliveries in the same sample. Use Workbench to inspect destination response codes and reconcile failures. An event's existence in Stripe does not establish delivery to this app.
- Production Supabase Auth currently allows sign-up and auto-confirms email. Registration now follows Supabase's sign-up settings. Because auto-confirm does not prove mailbox ownership, an invitation also requires possession of its token and a session matching its recipient. Decide whether to require email confirmation before rollout and verify redirect URLs, sign-in, and transactional email in the sandbox. Verify the existing portal configuration supports payment-method updates and invoice recovery.

## Approved cutover

1. Record the current production Vercel deployment and rollback target. Take a secure schema snapshot and a restricted billing reconciliation export. Compare existing user, company, membership, and subscription counts. Keep the webhook and success page reachable.
2. At the production edge, temporarily block POST requests to `/api/stripe/start-trial` so older deployments cannot issue untracked Checkout sessions. Verify the block on every production hostname that can serve the legacy route. Wait for outstanding legacy subscription sessions to complete or expire. Confirm in Stripe there are no open legacy subscription sessions. Leave invoice-payment Checkout outside this pause.
3. Apply the additive migration with Checkout paused. Confirm ledger backfill, private function grants, owner access, and delegated access. Verify the active Stripe subscription reconciles to eligible local state. Review any unverified accounts before lifting the pause.
4. Deploy the approved version with `BILLING_CHECKOUT_PAUSED=1` for the initial smoke check. Verify Vercel's production deployment status, commit, and alias. Verify signed webhook delivery, session auth, existing active users, and business and membership counts. Apply any separately approved Stripe event configuration changes.
5. Remove the pause after delivery and production checks pass. Keep customer-initiated billing available and observe webhook errors and access denials. Use only read-only production checks or explicitly approved fixtures.

## Rollback

Pause new subscription Checkout immediately using the production edge rule. Keep the eligibility ledger, existing subscription rows, and company records. Preserve webhook processing and return URLs for outstanding sessions. Reconcile Stripe against retained Supabase rows and roll forward when possible. For a code rollback, use a verified compatible build that keeps account-bound portal and company endpoints and preserves eligibility enforcement, or keep affected paths blocked until a corrected build is available. Reopening the legacy trial endpoint would bypass the ledger. Do not drop the migration as a routine rollback. Verify the resulting Vercel production alias, webhook delivery, active access, and delegated access before reopening Checkout.
